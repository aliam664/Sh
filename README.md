# 🃏 Bluff / Bid — بازی آنلاین چندنفره‌ی بلوف

بازی اجتماعی آنلاین تحت وب برای **۳ تا ۸ نفر**.
شما در یک **تماس صوتی جداگانه** (دیسکورد، واتس‌اپ، تلگرام) با هم صحبت می‌کنید و
این سایت فقط نقش **داور و تخته‌ی امتیاز** را بازی می‌کند.

> ⚠️ **این سایت هیچ صدایی پخش یا ضبط نمی‌کند.** نه WebRTC، نه میکروفون، نه هیچ دسترسی صوتی.

🔗 **نسخه‌ی زنده:** https://aliam664.github.io/Sh/

## 🎯 قوانین بازی

### پایه
- تعداد بازیکن: **حداقل ۳، حداکثر ۸**
- بازی از چند **دور (Round)** تشکیل می‌شود.
- در هر دور یک **موضوع** مطرح می‌شود (مثلاً «کشورهای قاره‌ی آسیا») و بازیکنان روی
  «چند مورد می‌توانم نام ببرم» **مناقصه** می‌کنند.

### ۱) شروع دور
میزبان موضوع را انتخاب می‌کند — از بانک سوال، «تصادفی»، یا یک موضوع دستی.

### ۲) مرحله‌ی مناقصه (Bidding)
- بازیکن اول عددی پیشنهاد می‌دهد: «من ۵ مورد می‌توانم بگویم».
- بازیکن بعدی فقط **دو گزینه** دارد: عدد را **بالا ببرد** یا دکمه‌ی **BLUFF** را بزند.
- ترتیب نمونه: `5 → 8 → 12 → …`
- عدد جدید باید **اکیداً بزرگ‌تر** باشد. `5 → 5` و `5 → 4` غیرمجازند.
- **سقف پیشنهاد:** برای سوال‌های بسته برابر تعداد جواب‌های موجود؛ برای سوال‌های آزاد سقف نرم **۳۰**.
- **بدون Pass.**
- ⏱ **تایمر نوبت: ۳۰ ثانیه.** اگر تمام شود، خودکار BLUFF ثبت می‌شود.
  *(بدون این تایمر، یک بازیکن غایب کل بازی را برای همیشه قفل می‌کند.)*
- بازیکن اولِ دور نمی‌تواند بلوف بزند، چون هنوز پیشنهادی وجود ندارد.

### ۳) مرحله‌ی چالش (Challenge)
وقتی کسی BLUFF زد:
- **آخرین پیشنهاددهنده** می‌شود **مدافع (Defender)**.
- او باید دقیقاً به تعداد آخرین پیشنهاد، مورد معتبر نام ببرد.
- ⏱ **تایمر: ۶۰ ثانیه.**
- مدافع جواب‌ها را در یک اینپوت سریع تایپ می‌کند و Enter می‌زند؛ سیستم لحظه‌ای اعتبارسنجی می‌کند.
- برای سوال‌های **آزاد**، میزبان کنار هر جواب دکمه‌ی ✔ / ✘ دارد.

### ۴) پایان دور
- به تعداد لازم مورد معتبر گفت ⇒ **موفق**
- تایمر تمام شد یا کم آورد ⇒ **شکست**
- **بازنده‌ی هر دور، دور بعد را شروع می‌کند.**

### ۵) پایان بازی
میزبان هنگام ساخت اتاق یکی را انتخاب می‌کند:
- **تعداد دور ثابت:** ۵ یا ۱۰ دور
- **امتیاز هدف:** اولین کسی که به امتیاز هدف (پیش‌فرض ۱۵) برسد

## 🏆 سیستم امتیازدهی

| رویداد | امتیاز |
|---|---|
| مدافع موفق شد (بلوف اشتباه بود) | مدافع **+۲** |
| بلوف درست بود (مدافع شکست خورد) | چالش‌کننده **+۱** |
| بازیکن شکست‌خورده | **−۲** |
| بلوف اشتباه (جریمه‌ی چالش بی‌جا) | چالش‌کننده **−۱** |

**چرا جریمه‌ی چالش بی‌جا؟** *(یادداشت طراح بازی)*
بدون آن، زدن BLUFF هیچ ریسکی ندارد و بازیکنان بی‌دلیل چالش می‌دهند؛ تعادل بازی به‌هم می‌ریزد.

- امتیاز می‌تواند **منفی** شود.
- هر تغییر امتیاز داخل یک **Firestore Transaction** انجام می‌شود تا race condition رخ ندهد.
- نتیجه‌ی هر دور در `history` ثبت می‌شود و **هرگز قابل ویرایش نیست**.

## ✅ اعتبارسنجی جواب‌ها

**سوال‌های بسته** (`isOpen: false`) خودکار بررسی می‌شوند:

1. **نرمال‌سازی** — حذف فاصله‌ی اضافه، تبدیل به حروف کوچک، یکسان‌سازی `ی/ي` و `ک/ك`،
   تبدیل ارقام فارسی/عربی به لاتین، حذف نیم‌فاصله و اعراب
2. **تکراری نبودن** — مقایسه با جواب‌های قبلی همان دور
3. **در موضوع بودن** — باید در لیست جواب‌ها یا نام‌های مستعار باشد
4. **تحمل غلط املایی** — الگوریتم **Levenshtein** با فاصله‌ی ≤ ۱ برای کلمات ۵+ حرفی
   (مثلاً «ویتنم» → «ویتنام» پذیرفته می‌شود)
5. **شمارش** تا رسیدن به عدد پیشنهاد

**سوال‌های آزاد** (`isOpen: true`) با **تایید دستی میزبان** بررسی می‌شوند؛ در حالت شک،
بقیه در تماس صوتی بحث می‌کنند و میزبان تصمیم می‌گیرد.

بازخورد بصری: 🟢 معتبر · 🔴 رد شد · 🟡 در انتظار تایید میزبان

**بانک سوال:** ۸۰ سوال در ۱۰ دسته (دقیقاً ۸ سوال در هر دسته)، مجموعاً ۹۷۵ گروه جواب با
نام‌های مستعار فارسی و انگلیسی.

`Countries` · `Marvel` · `DC` · `Movies` · `Anime` · `Football` · `Animals` · `Science` · `History` · `Games`

## 🚀 راه‌اندازی قدم‌به‌قدم

> این بخش برای کسی نوشته شده که **هیچ‌چیز از Firebase و GitHub بلد نیست**.
> کل فرایند حدود ۱۵ دقیقه طول می‌کشد و **کاملاً رایگان است** (نه کارت اعتباری، نه هزینه).

### گام ۱ — ساخت پروژه در Firebase

1. به [console.firebase.google.com](https://console.firebase.google.com) برو و با اکانت گوگل وارد شو.
2. روی **Add project** بزن.
3. یک نام بگذار (مثلاً `bluff-game`) و **Continue**.
4. Google Analytics را می‌توانی **خاموش** کنی (نیازی نیست) و **Create project** را بزن.

### گام ۲ — فعال‌سازی Anonymous Authentication

1. از منوی چپ: **Build → Authentication → Get started**
2. تب **Sign-in method** را باز کن.
3. در لیست، **Anonymous** را انتخاب کن.
4. کلید **Enable** را روشن کن و **Save**.

> بدون این گام هیچ‌کس نمی‌تواند وارد بازی شود.

### گام ۳ — ساخت Cloud Firestore

1. از منوی چپ: **Build → Firestore Database → Create database**
2. **Region** را انتخاب کن — نزدیک‌ترین به بازیکنان
   (برای ایران و خاورمیانه: `europe-west1` یا `europe-west3` معمولاً سریع‌ترین است).
   ⚠️ Region **بعداً قابل تغییر نیست**.
3. حالت شروع: **Start in production mode** را بزن (قوانین امنیتی را در گام ۵ می‌گذاریم).
4. **Create**.

### گام ۴ — کپی کردن Config

1. روی چرخ‌دنده‌ی بالای منوی چپ → **Project settings**
2. پایین صفحه بخش **Your apps** → آیکون **`</>`** (Web) را بزن.
3. یک نام مستعار بده (مثلاً `bluff-web`) و **Register app**.
   ✔️ تیک «Also set up Firebase Hosting» را **نزن** (ما روی GitHub Pages میزبانی می‌کنیم).
4. یک قطعه کد به تو نشان می‌دهد. مقادیر داخل `firebaseConfig` را کپی کن.
5. فایل **`js/firebase-config.js`** را باز کن و مقادیر را جایگزین `PASTE_HERE` کن:

```js
export const firebaseConfig = {
  apiKey:            "AIzaSy...",
  authDomain:        "bluff-game.firebaseapp.com",
  projectId:         "bluff-game",
  storageBucket:     "bluff-game.appspot.com",
  messagingSenderId: "123456789012",
  appId:             "1:123456789012:web:abcdef123456"
};
```

> 📌 **`js/firebase-config.js` تنها فایلی است که باید دست بزنی.** بقیه‌ی پروژه بدون هیچ ویرایشی کار می‌کند.

### گام ۵ — Deploy کردن قوانین امنیتی

**راه ساده (بدون نصب هیچ ابزاری):**

1. در کنسول: **Build → Firestore Database → تب Rules**
2. تمام محتوای فعلی را پاک کن.
3. کل محتوای فایل **`firestore.rules`** این پروژه را کپی کن و آنجا بچسبان.
4. **Publish** را بزن.

**راه حرفه‌ای (با Firebase CLI):**

```bash
npm install -g firebase-tools
firebase login
firebase init firestore     # فایل‌های موجود را overwrite نکن
firebase deploy --only firestore:rules,firestore:indexes
```

> 🔴 **این گام را رد نکن.** بدون آن یا هیچ‌کس دسترسی ندارد، یا (بدتر) همه به همه‌چیز دسترسی دارند.

### گام ۶ — ساخت ایندکس‌ها

پاکسازی خودکار اتاق‌های قدیمی به یک ایندکس ترکیبی نیاز دارد.

- **راه ساده:** بازی را اجرا کن؛ اگر ایندکس لازم باشد، در Console مرورگر یک لینک مستقیم
  «Create index» ظاهر می‌شود — رویش کلیک کن و **Create** بزن.
- **راه CLI:** `firebase deploy --only firestore:indexes` (فایل `firestore.indexes.json` آماده است).

### گام ۷ — آپلود روی GitHub

```bash
git clone https://github.com/<user>/<repo>.git
cd <repo>
# فایل‌های پروژه را اینجا کپی کن
git add .
git commit -m "Bluff / Bid game"
git push origin main
```

⚠️ **فایل `.nojekyll` حتماً در ریشه باشد** — بدون آن GitHub Pages پوشه‌ها و فایل‌هایی که با
`_` شروع می‌شوند را نادیده می‌گیرد و سایت خراب می‌شود. (این فایل در پروژه هست؛ حذفش نکن.)

### گام ۸ — فعال‌سازی GitHub Pages

1. در ریپازیتوری: **Settings → Pages**
2. **Source:** `Deploy from a branch`
3. **Branch:** `main` و پوشه: **`/ (root)`**
4. **Save**. بعد از حدود یک دقیقه، آدرس سایت نمایش داده می‌شود:
   `https://<user>.github.io/<repo>/`

### گام ۹ — افزودن دامنه به Authorized Domains

1. کنسول Firebase: **Authentication → Settings → Authorized domains**
2. **Add domain** → `<user>.github.io` را وارد کن → **Add**.

> بدون این گام، ورود کاربران با خطای `auth/unauthorized-domain` شکست می‌خورد.

### گام ۱۰ — فعال‌سازی App Check (اکیداً توصیه می‌شود)

بدون App Check، هر کسی با یک اسکریپت ساده می‌تواند مستقیم به دیتابیس تو بنویسد و
**سهمیه‌ی رایگانت را بسوزاند**.

1. یک کلید reCAPTCHA v3 از [google.com/recaptcha/admin](https://www.google.com/recaptcha/admin) بساز
   (نوع: **reCAPTCHA v3**، دامنه: `<user>.github.io`).
2. کنسول Firebase: **Build → App Check → Apps → اپ وب خودت → reCAPTCHA v3** و **Site key** را وارد کن.
3. در فایل `js/firebase-config.js` مقدار زیر را پر کن:

```js
export const RECAPTCHA_SITE_KEY = "6Lc...";
```

4. در بخش **App Check → APIs**، برای Cloud Firestore ابتدا حالت **Monitor** را بزن،
   و بعد از اطمینان از درست کار کردن، **Enforce** کن.

### گام ۱۱ — تست چندنفره

سایت را روی **سه دستگاه یا سه پنجره‌ی Incognito** باز کن و یک بازی کامل انجام بده.
[چک‌لیست تست](#-چکلیست-تست-نهایی) را دنبال کن.

### تصمیم‌های معماری کلیدی

**۱) `players` / `rounds` / `history` به‌صورت Subcollection، نه فیلد داخل سند اتاق**
دلیل: سقف ۱ مگابایتی هر سند، تداخل نوشتن هم‌زمان (write contention)، و امکان کنترل
دقیق‌تر با Security Rules.

**۲) صفحه‌ی نتیجه یک Overlay داخل `game.html` است، نه یک فایل جدا**
دلیل: تغییر صفحه بین دورها یعنی قطع و اتصال مجدد `onSnapshot`، پرش state و مصرف اضافه‌ی سهمیه.

**۳) تایمر هرگز در دیتابیس شمرده نمی‌شود**
فقط `timerStart` (سروری) و `timerDuration` ذخیره می‌شوند. هر کلاینت خودش با
`requestAnimationFrame` باقی‌مانده را حساب می‌کند. **اختلاف ساعت گوشی با سرور** اندازه‌گیری
و جبران می‌شود تا شمارش معکوس روی همه‌ی گوشی‌ها یکسان باشد (±۱ ثانیه).

**۴) Presence با Heartbeat — نه `onDisconnect()`**

> ⚠️ **نکته‌ی حیاتی:** Firestore معادل `onDisconnect()` **ندارد** — آن قابلیت فقط در
> Realtime Database وجود دارد. بدون راه‌حل زیر، وقتی اینترنت کسی قطع شود بازی روی نوبت او
> **برای همیشه قفل می‌شود.**

راه‌حل پیاده‌شده:
- هر بازیکن **هر ۱۵ ثانیه** فیلد `lastSeen: serverTimestamp()` را می‌نویسد.
- هر کلاینت **محلی** حساب می‌کند: `now − lastSeen > 40s` ⇒ آفلاین. (پس **هیچ نوشتن اضافه‌ای** ندارد.)
- بازیکن آفلاین در نوبتش **skip** می‌شود.
- `visibilitychange` و `pagehide` وضعیت را فوراً پاک می‌کنند.

**۵) Host Migration**
اگر میزبان بیش از **۴۰ ثانیه** آفلاین باشد، **قدیمی‌ترین بازیکن آنلاین** ادعای میزبانی می‌کند.
عملیات داخل **Transaction** انجام می‌شود تا دو نفر هم‌زمان میزبان نشوند، و Security Rules
فقط در همین شرایط اجازه‌ی تغییر `hostId` را می‌دهد.

**۶) Service Worker: HTML شبکه‌اول، دارایی‌ها کش‌اول**
اگر HTML را cache-first کنیم، بازیکنان با **دو نسخه‌ی متفاوت بازی** بازی می‌کنند — این در یک
بازی چندنفره یک باگ کشنده است. درخواست‌های Firestore و Auth **هرگز** کش نمی‌شوند.

**۷) هشدار عملکردی Glassmorphism**
`backdrop-filter: blur()` روی موبایل‌های میان‌رده FPS را به‌شدت پایین می‌آورد. بنابراین فقط روی
**۴ سطح کلیدی** استفاده شده (هدر، کارت موضوع، مودال، نوار پایین) و **هرگز روی کارت تک‌تک بازیکنان**.
همه‌ی انیمیشن‌ها فقط با `transform` و `opacity` (GPU-accelerated) هستند و `prefers-reduced-motion` رعایت می‌شود.

## 🔐 امنیت، مدل تهدید و محدودیت‌ها

### چیزهایی که کاملاً جلویشان گرفته شده

بازیکن عادی **نمی‌تواند**:
- ❌ امتیاز خودش یا دیگری را تغییر دهد
- ❌ نوبت را عوض کند یا بیرون از نوبتش Bid بزند
- ❌ به‌جای بازیکن دیگری کنشی ثبت کند
- ❌ عددی کمتر یا مساوی پیشنهاد فعلی ثبت کند *(در سطح Rules هم بررسی می‌شود)*
- ❌ رکورد History را ویرایش کند
- ❌ روی پروفایل کاربران دیگر بنویسد

### ⚠️ شفافیت مهندسی — این را حتماً بخوان

> در یک معماری **بدون سرور** (پلن Spark)، Security Rules فقط **شکل** داده را اعتبارسنجی
> می‌کند، نه **درستی منطق بازی** را.
>
> بنابراین جلوی تقلب **بازیکن عادی به‌طور کامل گرفته می‌شود**، ولی **میزبان** از طریق کنسول
> مرورگر تئوریک می‌تواند نتیجه را دستکاری کند — چون کسی جز او نیست که امتیازها را بنویسد.
>
> **امنیت ۱۰۰٪ فقط با Cloud Functions (نیازمند پلن Blaze) ممکن است.**
>
> در این پروژه مدل **Host-Authoritative + Rules سختگیرانه + History تغییرناپذیر** انتخاب شده،
> چون بازی دوستانه است و در تماس صوتی، تقلب فوراً لو می‌رود.

### درباره‌ی `apiKey`

**`apiKey` فایربیس رمز نیست** — یک شناسه‌ی عمومی است و لو رفتنش در گیت‌هاب **طبیعی و بی‌خطر** است.
هر اپ وب فایربیس آن را در سورس کلاینت دارد. محافظت واقعی از این‌ها می‌آید:

1. **Security Rules** — تنها خط دفاع واقعی داده
2. **Authorized Domains** — فقط `<user>.github.io` (گام ۹)
3. **App Check با reCAPTCHA v3** — جلوگیری از سوءاستفاده‌ی اسکریپتی و سوختن سهمیه (گام ۱۰)

### لایه‌های دیگر

- **Rate limiting** سمت کلاینت + قانون «حداقل فاصله‌ی زمانی بین دو نوشتن» در Rules
- **Sanitize کامل** همه‌ی ورودی‌ها (نام، جواب، موضوع دستی): حذف تگ HTML، کاراکترهای کنترلی و جهت‌دهی
- **بدون هیچ `innerHTML`** روی داده‌ی کاربر — همه‌چیز با `textContent` ساخته می‌شود
- **جواب‌ها رمزگذاری‌شده‌اند** تا با یک نگاه ساده در DevTools لو نروند
  *(یک «سد کاغذی» است نه امنیت واقعی — برای بازی دوستانه کافی است)*

### ⚠️ Anonymous Auth شکننده است

**Safari ITP** بعد از **۷ روز** بی‌فعالیتی حافظه‌ی سایت را پاک می‌کند و هویت کاربر از بین می‌رود.
همچنین پاک کردن دستی داده‌های مرورگر یا استفاده از حالت Incognito همین اثر را دارد.
در این حالت کاربر باید دوباره نام انتخاب کند و **آمار قبلی‌اش برنمی‌گردد**. این محدودیت **ذاتی**
Anonymous Authentication است و راه‌حلی جز افزودن ورود واقعی (گوگل/ایمیل) ندارد.

## 📊 برآورد سهمیه (پلن Spark)

سهمیه‌ی روزانه‌ی رایگان Firestore: **۵۰٬۰۰۰ خواندن** · **۲۰٬۰۰۰ نوشتن** · **۲۰٬۰۰۰ حذف**

برآورد یک بازی ۵ نفره و ۵ دوره (~۱۵ دقیقه):

| عملیات | تعداد تقریبی |
|---|---|
| نوشتن Heartbeat (۵ نفر × ۴ بار در دقیقه × ۱۵ دقیقه) | ~۳۰۰ |
| نوشتن کنش‌های بازی (Bid، Bluff، جواب، نتیجه) | ~۱۲۰ |
| خواندن‌های `onSnapshot` (هر تغییر × تعداد بازیکنان) | ~۲٬۰۰۰ |
| **جمع تقریبی هر بازی** | **~۴۰۰ نوشتن · ~۲٬۰۰۰ خواندن** |

⇒ با پلن رایگان تقریباً **۵۰ بازی در روز** بدون هیچ هزینه‌ای ممکن است.

**نکاتی که مصرف را پایین نگه می‌دارند:**
- تشخیص آفلاین بودن **محلی** محاسبه می‌شود، نه با نوشتن در دیتابیس
- تایمرها هرگز در دیتابیس شمرده نمی‌شوند
- صفحه‌ی نتیجه Overlay است، پس listenerها دوباره وصل نمی‌شوند
- **پاکسازی تنبل:** هنگام ورود به Lobby، اتاق‌های قدیمی‌تر از ۲۴ ساعتِ خودت حذف می‌شوند
