# معماری فنی «رمزو» — شبکهٔ محلی، پروتکل، نگاشت کد

> سند تکمیلی GDD. هدف: فردی که کد را نمی‌شناسد هم بفهمد سیستم چطور ساخته شده و هر تصمیم چرا گرفته شده.

---

## ۱. تصمیم‌های کلیدی و دلیلشان

| تصمیم | انتخاب | چرا |
|---|---|---|
| زبان/رابط کاربری | **Kotlin + Jetpack Compose (Material 3)** | اندروید-only است؛ نیتیو خالص = سبک‌ترین APK، بهترین عملکرد، ساده‌ترین اجرا در Android Studio |
| معماری نرم‌افزار | **MVVM تک‌فعالیتی** با StateFlow | صفحه‌ها فقط «بازتاب» وضعیت‌اند؛ تست‌پذیر و تمیز |
| الگوی شبکه | **ستاره‌ای، میزبانِ معتمد (Authoritative Host)** | گوشی میزبان هم «سرور اتاق» است هم بازیکن؛ داوری و امتیاز فقط اونجا |
| لایهٔ انتقال | **TCP با پیام‌های JSON خط‌به‌خط (NDJSON)** | بازی نوبت‌محور است؛ حجم پیام‌ها ناچیز (هر حدس <۱KB)؛ TCP ترتیب و رسیدن را رایگان تضمین می‌کند و روی LAN پینگ ۵–۲۰ms دارد. UDP/ENet برای این ژانر فقط پیچیدگی اضافه می‌آورد |
| کشف اتاق | **UDP Broadcast** + لیست زنده + **پشتیبان IP دستی** | اندروید-only است، پس مزیت Bonjour لازم نیست؛ اگر روی یک شبکه broadcast بسته بود، IP دستی همیشه کار می‌کند. دریافت‌کننده MulticastLock می‌گیرد (رفتار بعضی گوشی‌ها) |
| JSON | `org.json` (داخلی اندروید) | بدون وابستگی اضافه؛ پایدار و ساده برای ۱۲ نوع پیام |
| همزمانی | **یک رشتهٔ منطقی تکی** برای همهٔ رویدادهای بازی + رشته‌های I/O جدا | هیچ قفل‌گذاری/Race در منطق بازی؛ ساده و قابل‌استدلال |

## ۲. پروتکل پیام‌ها (همه یک JSON در هر خط، `\n` پایانی)

**جهت:** `C→S` کلاینت به میزبان | `S→C` میزبان به کلاینت(ها)

| پیام | جهت | فیلدها | زمان |
|---|---|---|---|
| `hello` | C→S | `name`, `proto` | اولین پیام بلافاصله پس از اتصال |
| `err` | S→C | `code` | خطای ورود (`room_full` / `proto_mismatch` / `game_started`) سپس قطع؛ یا خطای درون بازی (`guesses_over`) |
| `welcome` | S→C | `id`, `room` | پذیرش کلاینت — اختصاص شناسه |
| `lobby` | S→همه | `players:[{id,name,host}]` | هر تغییر در لابی |
| `roundStart` | S→همه | `round`, `holder`, `holderName`, `max` | شروع دور |
| `secret` | C→S | `s` (۴ رقم) | فقط صاحب رمز |
| `secretAck` | S→C | `ok`, `why` | پذیرش/رد رمز |
| `guess` | C→S | `g` | ارسال حدس |
| `result` | S→آن کلاینت | `g`, `c:[0/1/2×4]`, `solved`, `left` | نتیجهٔ رنگ‌بندی فقط برای صاحب حدس (۰=سبز،۱=زرد،۲=قرمز) |
| `progress` | S→همه | `id`, `used`, `solved` | پیشرفت عمومی (بدون محتوای حدس) |
| `roundEnd` | S→همه | `winner`, `winnerName`, `secret`, `scores:[{id,score}]`, `nextHolder`, `last` | پایان دور — حالا رمز افشا می‌شود |
| `bye` | S→همه | `why` | بستن اتاق توسط میزبان |

نمونهٔ واقعی:
```json
{"t":"result","g":"5211","c":[1,1,1,1],"solved":false,"left":8}
{"t":"roundEnd","winner":3,"winnerName":"سارا","secret":"1125","scores":[{"id":0,"score":0},{"id":3,"score":1}],"nextHolder":1,"last":false}
```

**اصول امنیت/صداقت:** رمز هرگز از سرور به بیرون نمی‌رود (جز در `roundEnd`)؛ محتوای حدس هر بازیکن فقط به خودش برمی‌گردد؛ میزبان منبع واحد حقیقت (single source of truth) است.

**دو قانون مقررات‌محور v1:**
- سیگنال «رمز قفل شد، حدس‌زدن باز است» = پیام `progress` با `id` برابر **۱‑** (سنتینل `SIGNAL_SECRET_READY`).
- **ورود وسط بازی نداریم:** کلاینت تازه هنگام بازیِ جاری کد `game_started` می‌گیرد و مؤدبانه قطع می‌شود (بازیکنِ قطع‌شده وسط دور هم با «مصرف‌شده‌تلقی‌شدن» حدس‌هایش باعث قفل‌شدن دور نمی‌شود و خروج صاحب رمز = ابطال همان دور).

## ۳. کشف اتاق (Discovery)

1. میزبان هنگام بازبودن لابی، هر ۱ ثانیه روی `255.255.255.255:47777` پخش می‌کند: `{"m":"RAMZO1","room":"بازیِ علی","ip":"192.168.43.1","port":48000}`
2. کلاینت در صفحهٔ خانه گوش می‌دهد (DatagramSocket + **MulticastLock** برای گوشی‌هایی که بدون آن broadcast را تحویل نمی‌دهند)، هر اتاق ۴ ثانیه زنده می‌ماند و بعد از لیست حذف می‌شود.
3. **پشتیبان دائمی:** ورود IP دستی + نمایش درشت IP روی صفحهٔ میزبان (برای شبکه‌هایی با Client Isolation).

## ۴. رشته‌ها و چرخهٔ عمر

```
UI (Main) ── StateFlow ──▶ صفحه‌های Compose
   │  ▲
   │  └──────────── GameViewModel ───────────┐
   │                                         │  همهٔ رویدادها روی
   ▼                                         ▼  «rشتهٔ منطقی تکی»
LanClient/LanHost (رشته‌های Socket I/O) ──▶ Game Logic (داوری، امتیاز، چرخهٔ دور)
                                            + Advertiser/RoomScanner (Thread + Coroutine)
```

- هر سوکت یک رشتهٔ خواندن دارد؛ `PrintWriter` با `@Synchronized` نوشته می‌شود.
- قطع‌شدن کلاینت = EOF/خطای سوکت → رویداد روی رشتهٔ منطقی → به‌روزرسانی لابی/دور.
- چرخهٔ دور (میزبان): `RoundStart` → انتظار `secret` → پذیرش `guess`ها (ارزیابی → `result`+`progress`) → شرط پایان (حل‌شدن یا اتمام سقف همه) → `roundEnd` → دکمهٔ میزبان → دور بعد.
